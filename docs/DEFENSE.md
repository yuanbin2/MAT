## 1. 项目背景与题目

- **场景**：5 家门店的连锁餐饮品牌。运营每天要回答两类问题：
  1. **数字是多少** → 查数据库（`data/pos.db`，约 1.8 万行销售记录）；
  2. **为什么、按规定怎么办** → 查公司知识库（`knowledge_base/`，35 篇文档）。
  真正有用的问题往往两样都要，例如"S03 六月第二周营业额为什么这么低？"。
- **陷阱**：数据是真实 POS 导出——有重复、缺失、格式不一、脏外键；知识库也和真实一样——有过期旧版本、互相矛盾的说法、估算的数字。**不是每份文档都可信**。
- **系统"今天"固定为 2026-09-01**，与真实日期无关（`kbqa/config.py` 里写死，是运营口径）。
- **题目形态**：四关递进，总评 100 分 = 作业 70 分 + 现场调试 40 分钟 30 分。

| 关卡 | 内容 | 分值 |
|---|---|---|
| 第一关 | 数据看板（指标 API + 前端） | 12 |
| 第二关 | 接手并修好 RAG 服务（检索质量 + DEBUG_LOG 根因质量） | 20 |
| 第三关 | 混合问答（数据 + 文档双证据，隐藏题库自动评分） | 22 |
| 第四关 | 可调试性与回归 | 8 |
| Git 过程 + AI_USAGE + 可复现性 | — | 8 |

**评审怎么验**（决定了我所有设计取舍）：
1. 按 README 在干净环境跑起来（先不配 Key）；
2. 按 `LLM_SETUP.md` 切到 DeepSeek `deepseek-flash`、换他们的 Key 跑公开题库，对照 `EVAL_REPORT.md`；
3. **把 `data/` 和 `knowledge_base/` 换成另一份（数字不同、文档有增改）**，执行重建命令，用**隐藏题库**再跑——所以任何数字/答案/文档内容都不能写死，索引必须能跟着知识库变；
4. 读 `DEBUG_LOG.md`、`AI_USAGE.md`、提交历史；
5. 通过者进入现场调试。

## 2. 总体架构与选型

```
┌────────────┐   /api/*（Vite 代理）   ┌──────────────────────────┐
│  前端看板   │ ───────────────────────▶ │  FastAPI（starter/kbqa）  │
│ Vue3+TS    │                          │  server.py  路由/参数校验  │
│ Vite+ECharts│ ◀─────────────────────── │  service.py 组装/编排      │
│  + AI 助手  │       JSON               │  planner.py 规划/追问     │
└────────────┘                          │  answerer/hybrid 取证作答 │
                                        │  live.py   模型编排/核验  │
                                        │  tools.py   指标查询       │
                                        │  sqlguard.py 只读 SQL 闸门 │
                                        │  cleaning.py 清洗（KB-001）│
                                        │  retriever.py 检索/版本   │
                                        └───────────┬──────────────┘
                                                    │ 只读（mode=ro）
                              ┌─────────────────────┴─────────────────┐
                              │ var/clean.db（清洗后）   .cache/index.json│
                              ▲                                       ▲
                        data/pos.db                        knowledge_base/
                     （原始 POS 导出）                        （35 篇文档）
```

**选型理由**（答辩被问"为什么"时的答案）：
- **后端保留 starter 的 FastAPI**：契约接口都在这条服务上，评测脚本也按它来，重写会破坏兼容、无收益。
- **前端 Vue 3 + TS + Vite + ECharts**：单页看板规模小，不需要后台模板；ECharts 按需引入，gzip 约 190 KB。
- **清洗/指标纯 Python + SQLite**：1.8 万行不需要额外引擎；金额以"分"为整数单位避免浮点误差，客单价用 `ROUND_HALF_UP`。

**三条贯穿始终的设计原则**：
1. **数字只来自真实查询，事实只来自本轮检索原文**——模型可以"出候选"，但代码核验不过就不采用；
2. **数据库连接只读**（`mode=ro` + `PRAGMA query_only`），模型能调的 `run_sql` 再过一层只读语法闸门；
3. **可复现**——换数据/知识库后 `make rebuild` 就能出新结果，代码里零硬编码数字。

## 4. 第一关：数据看板（12 分）

**目标**：按契约实现 `/api/metrics/summary`、`/api/metrics/daily`；前端做日期/门店筛选 + 营业额趋势图 + Top 10 商品表 + 数据质量区；README 3 步跑起来。

**我做了什么**：
- 清洗管线 `cleaning.py`：从原始 `pos.db` 生成 `var/clean.db`（去重、删脏行、统一日期、算退款）；
- 指标口径严格按 **KB-001《指标口径手册 v3》**（现行版，2026-05-01 生效）；
- 前端：`MetricCards`（总览卡）、`TrendChart`（ECharts 趋势）、`TopProducts`（Top10）、`DataQuality`（数据质量）、`FilterBar`（筛选）、`GlossaryModal`（口径说明）。

**遇到的真正难点——口径歧义**（这是第一关最容易被问倒的地方）：
- 数据"脏"到什么程度：有重复行、有缺失金额、有 `DD-MM-YYYY` 这种日在前格式、有 `2026-13-45` 这种假日期、退款到底算不算营业额。
- 前同事的交接文档（`HANDOVER.md`）里还有一句"月底数字对不太上，应该是四舍五入的事"——实际上根子是**口径理解错了**。

**我的取舍（全部有 KB-001 v3 依据，答辩可逐条报）**：

| 点 | 取舍 | 依据 |
|---|---|---|
| 退款 | 计入净营业额（负数相减），退款额单独绝对值展示 | v3 §4（v2 的"剔除退款行"已废止） |
| 有效订单数 | 不同 `order_id` 个数，多行订单算 1 单 | v3 §4 |
| 客单价 | 净营业额 ÷ 有效订单数，`ROUND_HALF_UP` 留 2 位 | v3 §4 |
| 金额为空 | 直接剔除，不按建档价回填 | v3 §3.2 |
| 日期格式 | 三种合法格式；假日期判为无法解析 | v3 §2.2 |
| 重复行 | 七字段规范化后完全一致才判重；同订单号不同商品行保留 | v3 §3.6 / §7.3 |

**质量保障**：`test_cleaning_rules.py`（清洗规则）、`test_metrics_rules.py`（指标口径）、`test_golden_values.py`（黄金值，把已知营业额/订单数写死成断言，防止口径一改数值就漂）。

## 5. 第二关：修好 RAG 服务（20 分，核心）

**接手时的反差**：交接文档说"检索命中率 95%、测试全绿"，实测公开题库 **17 分**——`doc` 和 `version` 全是 0 分，`hybrid` 也是 0 分。这暴露了第一个教训：**别人说的"命中率"不等于评测分数，测试绿不代表没 bug**。

**方法论（这是这一关的得分点，也是现场调试的预演）**：
1. 先用评测拿**基线**（17 分）；
2. 按数据流**分层**（装载→切块→分词→召回→排序→版本→路由→取证→安全），一层修完才看得见下一层；
3. 每个缺陷一条 `DEBUG_LOG.md`，六段式：**现象 / 假设 / 验证 / 根因(文件+行) / 修复(commit) / 回归测试(带红证)**；
4. **先写一个会红的测试，再修**——提交顺序就是"红测试 → 修复"，评审要求看的正是这个顺序。

**40 个缺陷（D1–D40）分 10 层**，举最有代表性的几类（答辩挑 2–3 个讲透即可）：

| 层 | 缺陷 | 一句话根因 | 修复要点 |
|---|---|---|---|
| 1 装载/切块/分词 | D1 中文整句被当一个词 | 分词器按空格切，中文没空格 → 检索无交集 | 引入中文分词 + 别名扩写 |
| 1 | D2 超 300 字文档末尾被丢 | `range(0, len-300, 300)` 的终点切不到最后不足一块的内容 | 覆盖全文切块（末尾不足一块也保留）+ 带章节标题上下文 |
| 1 | D3 HTML 带标签入库 | 未剥标签 → FAQ 检索被 `<b>` 污染 | 先转纯文本再切 |
| 1 | D4 字段名写 `state` 读 `status` | 版本过滤字段名不一致 | 统一字段名 |
| 2 召回/排序/版本 | D5 命中后重写 doc_id | 构造命中把编号改错 → 正文对不上号 | 用真实文件名 |
| 2 | D6 版本过滤在取 top-k 之后 | 先截断再过滤 → 结果不足 top_k | 先过滤再取 top-k |
| 2 | D7 候选句升序排序 | 排序方向写反，优先选最低分 | 降序 |
| 2 | D8 整篇文档拼进 answer | 无截断 → 超长 + 数字轰炸 | 只取相关片段 |
| 3 路由/取证/追问/安全 | D9 "多少/多久"一刀切路由到库 | 中文疑问词误判 | 语义 + 文档关键词联合判断 |
| 3 | D10 会话未按 session_id 隔离 | 跨用户串线 | 按 session 隔离且传给规划器 |
| 3 | D11 写操作/注入未接安全 | 无拦截 | 接入安全判断 |

**关键证据**：检索 `6/15 → 15/15`、文档 `0/16 → 16/16`、版本 `0/6 → 6/6`——这三类恰好对应 starter 的三大系统性缺陷（分词、版本过滤、路由），是分数从 17 跳到 100 的主因。

## 6. 第三关：混合问答（22 分，核心）

**目标**：`/api/chat` 用自然语言回答三类问题——只查库、只查文档、两样都要（"618 当天 S02 的牛肉poke 卖了多少，达到目标了吗？"）。

**硬性要求 → 我的实现映射**（答辩可直接按这张表讲）：

| 硬性要求 | 我的实现 |
|---|---|
| 数字必须来自真实查询，给 `data_evidence` | `tools.py` 真实跑 SQL，回答里数字严格对应工具结果 |
| 文档事实给 `citations`，`quote` 是原文连续文字 | 引用取自本轮检索片段，逐字校验 |
| 新旧版本用"当前有效版"，问"当时"用当时版 | 版本过滤（`effective_from/effective_to`） |
| 数字冲突怎么办 | 按口径手册"以数据库为准，文档作背景"的成文规定 |
| 没有就不编 | 结构化拒答（`refusal`），明确说"不知道" |
| 文档只当资料，不执行；删改数据/套系统信息要拒 | 安全判 + 只读 SQL + 提示注入拦截 |
| 追问（"那 7 月呢"）+ session 隔离 | 会话按 `session_id` 隔离，历史传给规划器 |
| 切 DeepSeek 不改代码 + Key 不入库 + 无 Key 能启动 | 三环境变量 `LLM_BASE_URL/LLM_API_KEY/LLM_MODEL` + `.env`（已 gitignore）+ mock 降级 |
| 交 `LLM_SETUP.md` | 已交，含 `llm_gateway.py preflight` 输出 |

**live 编排的核心思想（这关的灵魂，答辩重点讲）**：
模型不是"直接回答"，而是**只出候选**。代码拿模型产出的候选做三件事：
1. **数字核验**：回答里的经营数字必须对应真实的工具调用结果（白名单来源，防止从 SQL 文本/字段名/截断说明里"偷"数字）；
2. **引用核验**：文档事实必须对应本轮检索到的片段原文；
3. **范围核验**：工具参数必须落在 Plan 划定的范围里。
核验不过 → 回退本地 Answerer 并在 trace 里标明原因。**这样即使模型胡说，系统也不会把错误数字/假引用放出去**。

**只读边界与安全（分层 4/5/6，D12–D23）**：
- `run_sql` 只接受单条只读查询（`SELECT`/`WITH … FROM`），拒绝 `sqlite_master`/`sqlite_schema`/`pragma_*` 等内部对象、`file:` 路径与扩展加载，且只能访问业务表白名单 `sales_clean/stores/products`；
- 连接本身 `mode=ro` + `query_only`——**词法闸门 + 连接层只读双保险**，任一层单独都不足；
- 证据体积有上限（防单条 `data_evidence.result` 超 4096 字节）；检索内容**去指令化**后再送模型（防文档里藏 prompt 注入）。

**质量**：mock 100/100；live StepFun 100/100；接入预检 16 场景 P1–P14 **13 项通过 + P14 未检查**（未检查原因已在 `LLM_SETUP.md` 写明，不粉饰）。

## 7. 第四关：可调试性（8 分）

**目标**：答错之后能多快找到原因。

**我做了什么**：
- **trace 全程记录**（`trace.py`）：规划、检索命中与过滤原因、真实工具调用与结果、完整模型请求/响应、每步耗时、错误——落盘前**脱敏**（擦 Key）、有界（最近 200 条）、持久化、跨重启编号不重复；
- **调试面板**（前端 `TracePanel.vue`）：按排查顺序展示检索到了哪些片段、各多少分、哪些被过滤、执行了什么查询、最终提示词、每步耗时；
- **评测即回归**：`eval/check_regression.py` 对比 mock 基线，退步/漏题/坏报告 → 非零退出；接进 CI；支持 `--subset` 局部比对（调试时只看部分类别）；
- **自拟题 15 题**（`eval/extra_questions.jsonl`，29/29）：覆盖公开题库没测到的追问隔离、问题改写等，
  含 X14/X15 两道「文档+数据夹在同一句」的夹带句（复盘轮 D41 的回归题）；
- **新增文档演练**（`eval/drill_new_doc.py`）：现场往知识库加文档，看系统多久能答上——这正对评审现场调试的第二项。

**过程中暴露的两个"自己引入的缺陷"（诚实的加分项）**：
- D29：新增 `.env` 测试把 `os.environ` 泄漏给后续用例，导致无关用例去请求真实模型——测试隔离没做好；
- D31：演练用临时知识库重建，把索引写进了仓库跟踪的 `.cache/index.json`。
把"自己踩的坑"也记进 DEBUG_LOG，反而证明调试方法是真的。

**现场调试方法论**（`DEBUGGING.md`）：从 trace_id 出发 → 看规划对不对 → 看检索命中/过滤 → 看工具调用与结果 → 看最终提示词 → 定位根因 → 用"还原旧写法会红"验证修复。先复现、看证据，不猜。

## 8. 跨平台一致性（隐藏考点，最容易在隐藏题库翻车的地方）

**问题**：同一份 `knowledge_base`，Windows 提交的索引键 `b0da151d…`，Ubuntu 重建得到 `d693fbdd…`，Ubuntu 上两条索引守门测试失败。

**根因（两个，都与 OS 相关）**：
1. `core.autocrlf=true` 让 Windows 工作区是 CRLF、Ubuntu 是 LF；而 `content_key` 用 `read_bytes()` 哈希**原始字节**，`Document.text` 也原样保留 `\r` → 键与正文都不同；
2. `sorted(rglob)` 比较的是 `Path` 对象，Windows 大小写不敏感排序 vs Linux 大小写敏感排序 → 顺序不同。

**修复**：`read_text_normalized()` 把 `\r\n`/孤立 `\r` 统一折成 `\n`（哈希与入库都走它）；`kb_files_sorted()` 按 `as_posix()` 字符串排（平台无关）。新键 **`fc3eebbb…`**。

**为什么重要**：评审会把 `data/` 和 `knowledge_base/` 换成另一份再跑——索引必须能跟着知识库稳定重建，且 CI 里 `rebuild` 后 `git diff --exit-code -- starter/.cache/index.json` 必须干净。如果跨平台不一致，隐藏题库在 Linux 评审机上直接崩。新增 `test_crossplatform_index.py` 6 例覆盖三种换行 + 大小写排序 + 整份索引字节一致。

## 9. 质量保障体系（总结，答辩收尾用）

1. **分层测试**：清洗/指标/分词/切块/安全/只读 SQL/证据体积/live 取证/trace/索引一致性/夹带句识别/证据数字组合上限，共 240 个；
2. **评测 + 回归门禁 + CI**：mock 基线 100 分，任何改动跑一遍就知道涨跌；
3. **红绿证据**：每个缺陷都"先红后绿"，防止"看起来修好了其实没修对"；
4. **换模型验证**：StepFun 100 / MiMo 98 的对比证明了**代码质量不绑定单一模型**——掉分只落在模型的检索深度与追问判断上，不是 pipeline 缺陷；
5. **安全与脱敏**：Key 不入库（`.gitignore` + 机器闸门扫 `sk-`/`tp-`/`Bearer`/`token`）、trace 落盘前擦 Key、评测逐题结果脱敏后归档 `docs/eval/`；
6. **交付前通读复盘**：把自己当接手人把整套代码读一遍，专找"文档里写了、测试没覆盖、于是从来没被执行过"的路径——就这样发现了 D41（`two_part` 开关被写死，两条合并路径是死代码，一句话问了两件事只答一半）。**满分不等于没有死代码**，这是我最想讲的一条。

## 10. 高频追问预判与回答要点

**Q1：为什么不用向量检索？**
检索是纯 BM25 + 别名扩写。理由：①知识库只有 35 篇，BM25 已覆盖公开题库全部题；②现场换知识库必须能即时重建，向量模型会引入网络依赖和跨平台不确定性；③别名表的 distinctive token（`salmon`→三文鱼poke）已解决跨语言。这是明确记录在"已知边界"里的取舍，不是遗漏。

**Q2：live 模式下模型胡说怎么办？**
模型只出候选，代码核验数字白名单、引用逐字、参数范围，不过就回退本地 Answerer 并在 trace 标因。所以 live 质量受检索质量约束，检索是确定性的。

**Q3：`run_sql` 的 SQL 闸门是词法级，能被绕过吗？**
它是词法闸门（已排除注释/字符串误伤）+ 内部对象拦截，但**真正的最后防线是连接层 `mode=ro`**——两者同时生效，任一层单独都不足。这是"belt and suspenders"的诚实表述。

**Q4：日期类数字为什么不需要证据支撑？**
live 的"数字必须来自真实查询"是**面向数值的白名单**：日期写法与编号（S02/P06/KB-013）不参与校验，是有意取舍，已在文档写明。

**Q5：DeepSeek 为什么还没跑？**
本机没有 DeepSeek Key。接入已用预检（fake 模型）+ 打桩单元测试验证到 P1–P13，`LLM_SETUP.md` 就是"照着切一定能切过去"的说明。评审换 Key 跑是设计内的。

**Q6：换数据/换知识库后怎么保证还答得对？**
代码零硬编码数字；索引由 `content_key` 感知知识库变化自动失效重建；新增文档演练 + 索引守门测试 + CI rebuild 后 diff 校验，三重保证。

**Q7：追问（「那 7 月呢」）怎么实现的？会话怎么隔离？**
`followup.py` 先把追问还原成完整问题（继承上一轮的时间窗/门店/商品/指标槽位），再进规划器；
会话按 `session_id` 分字典隔离（`sessions.py`），只有成功回答才写历史，拒答/反问不污染槽位。
前端把 `session_id` 与消息记录存进 `sessionStorage`，所以**刷新页面后续得上聊**（追问依然能补全），
点「新建会话」才是真的开新会话——这个缺口是我通读时发现并修掉的（D42），
浏览器脚本 `verify-chat-session.mjs` 7 项检查盯着。仍然成立的边界：后端会话历史在进程内存里、
有界（500×6），服务重启后从零开始，这是不引入会话存储依赖的有意取舍。

**Q8：公开题库 100 分，怎么保证没有漏掉的需求？**
我做了两件事：①把整套代码当接手材料通读，找"开关被写死/路径从不上线"的问题，发现了 D41（文档+数据夹在同一句只答一半），并补了 X14/X15 两道夹带句进自拟题库；②自拟题库专门补公开题库不覆盖的形态——追问隔离、时间歧义反问、无数据拒答、闭区间精确值、周报估算 vs 实绩、历史版本、注入改写。隐藏题库答错时，先看 trace 再动手，方法在 `DEBUGGING.md`。

## 11. 现场调试环节打法（40 分钟，屏幕共享）

1. **被指到答错的题** → 先看 `trace_id`，打开调试面板或读 `var/traces/*.json`，**先复现、不先猜**；
2. 按顺序看：规划对不对 → 检索命中/过滤对不对 → 工具调用与结果 → 最终提示词 → 哪一步断了；
3. 定位到根因后，**用"还原旧写法会红"证明**（而不是直接改完说"应该好了"）；
4. 修完跑一遍 `check_regression.py` 确认没修坏别的。
5. **现场加新文档** → 展示 `make rebuild` 后能答上，且 `git diff -- starter/.cache/index.json` 干净。
全程可以用 AI 工具——重点是让评审看到"看证据、讲方法"，而不是背答案。
